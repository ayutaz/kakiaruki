# マイルストーン品質・判断ゲート

更新日: 2026-09-14

## 1. 目的

各マイルストーンについて、「実装済み」「技術検証済み」「体験承認済み」「公開承認済み」を混同しないための運用ルールを定めます。各マイルストーンの受入条件そのものは、対応する検証記録（[docs/11](11-p0-technical-validation.md)、[docs/14](14-m1-simulation-validation.md)〜[docs/20](20-m7-release-readiness.md)）が合否とともに持っています。

この文書は、テスト技法全般を定める [テスト・品質・性能計画](08-test-quality-and-performance.md) を置き換えません。ここでは各マイルストーンを閉じるために必要な証拠と、人の判断が必要な境界を扱います。

## 2. 状態の定義

| 状態 | 意味 |
|---|---|
| 未着手 | 実装も失敗テストも開始していない |
| Red | 期待する振る舞いを表す試験が、意図した理由で失敗している |
| 実装中 | 一部の試験は通るが、受入条件または文書が未完了 |
| 技術検証済み | 自動試験、型検査、build、必要な実測が合格した |
| 手動確認待ち | 技術条件は合格したが、人による体験・見た目・権利確認が必要 |
| 完了 | 全受入条件、証拠、必要な手動確認、文書更新が揃った |
| 保留 | 外部判断、方針変更、解消すべきリスクがあり進めない |

`技術検証済み` は `体験品質が良い` または `公開可能` を意味しません。

## 3. 全マイルストーン共通の完了条件

各マイルストーンは、次をすべて満たした時だけ完了にします。

- 受入条件を自動試験または明記した手動確認で検証している。
- 実装は失敗テストを先に作り、Redの理由を確認してからGreenへ進めている。
- 主要な分岐または配線を外すと試験が失敗することを確認している。
- `npm run verify` が成功している。
- 数値、Seed、ブラウザ、実行環境、試験対象を再現できる形で記録している。
- 実装とdocsの記述が一致している。
- 未完了、未確認、例外、既知の制約を隠さず記録している。
- 次のマイルストーンへ持ち越す項目と、その所有先が明確である。
- 人の判断が必要な項目を、自動試験の成功だけで完了扱いにしていない。

## 4. 実装と検証の標準手順

```text
受入条件を固定
  -> failing testを追加
  -> Redの失敗理由を確認
  -> 最小実装
  -> Greenを確認
  -> refactor
  -> mutation / wiring-disconnection proof
  -> integration / browser / performance検証
  -> docsと既知リスクを更新
  -> milestone gate判定
```

受入条件の数値は測定開始前に固定します。実行結果を見た後に閾値を変更する場合は、元の結果、変更理由、影響、再試験結果を残します。

## 5. 必須証拠のマトリクス

| Milestone | 自動試験 | 実測 | Browser | 手動判断 | 必須記録 |
|---|---|---|---|---|---|
| M1 | unit / contract / integration | 10,000 step、100 cleanup | 任意 | 不要 | Graph契約、lifecycle結果 |
| M2 | population / isolation / cleanup | Pop 1／8／32、100世代相当 | 必須 | engine継続判断 | throughput、p95、heap傾向 |
| M3 | GA / seed / replay /対照群 | 5 Seed、50世代 | 可視化確認 | 進化の差を理解できるか | Seed別統計、best Genome |
| M4 | stroke fixture / validation | event頻度差 | 必須 | error説明の理解性 | fixtureと変換例 |
| M5 | branch / snap / undo / loop | 長時間loopは条件付き | 必須 | 曖昧入力とloop採用 | 形状別期待Graph |
| M6 | state / integration / E2E | speed、停止・再開 | 必須 | 体験flow承認 | E2E結果、手動review |
| M7 | regression / recovery | 100世代、30分、build性能 | Chromium / Firefox | 権利・公開判断 | release candidate記録 |

## 6. マイルストーンごとの判断項目

### M1終了時

- Graphから物理構造への変換契約を確定できるか。
- 単一個体の生成・cleanupに資源漏れがないか。
- M2のlane方式へ拡張可能な境界になっているか。

### M2終了時

- Phaser Box2Dを継続採用するか。
- Population 32を維持するか、個体数を変更するか。
- Main threadのまま進めるか、Worker spikeを挟むか。

### M3終了時

- 進化群が対照群を上回ったか。
- 数値だけでなく、世代変化を人が理解できるか。
- Fitnessまたはcontroller表現の再設計が必要か。

### M4終了時

- 単純な一筆入力だけで学習体験が成立するか。
- validation errorがユーザーに修正方法を伝えられるか。
- M5の枝分かれを追加してもGraph契約を維持できるか。

### M5終了時

- 閉ループをMVPへ含めるか、明示的に対象外とするか。
- 自己交差を関節として扱う範囲をどこまでにするか。
- 最大骨数と最大Node次数を確定するか。

### M6終了時

- 人が「描いた形が動きを学んだ」と理解できるか。
- UI、説明、速度、リプレイが観察を助けているか。
- M7のrelease candidateへ進める体験品質か。

### M7終了時

- 技術的に公開可能か。
- 体験品質が公開水準か。
- 名称、UI、アセット、ライセンスが独立実装として承認されたか。
- 公開する、条件付きで公開する、保留する、のどれを選ぶか。

## 7. ユーザー承認が必要な境界

次の操作または決定は、技術マイルストーンの自動的な続きとして実行しません。

- Godotまたは別engineへの切替。
- M3の進化方式をGA以外へ変更。
- 閉ループをMVP必須へ変更。
- mobile、Safari、オンライン保存を対象へ追加。
- 製品名、アート、音、原作への言及方法の確定。
- アカウント、ランキング、課金、外部APIの導入。
- 外部hostへのdeploymentまたは一般公開。

## 8. 証拠記録の形式

各マイルストーン完了時に、`docs`へ検証記録を1つ追加します。

```text
docs/
  14-m1-simulation-validation.md   作成済み
  15-m2-population-performance.md  作成済み
  16-m3-evolution-validation.md    作成済み
  17-m4-stroke-input-validation.md 作成済み
  18-m5-branching-validation.md    作成済み
  19-m6-experience-review.md       作成済み
  20-m7-release-readiness.md       作成済み
```

各マイルストーンの**実装計画**（タスク分解とTDDの手順書）は、リリース時に削除しました。実装が終われば役目を終える作業文書で、成果と根拠は検証記録が持っているためです。必要なら git 履歴から取り出せます。

各記録には最低限、次を含めます。

1. 対象commitまたは成果物hash。
2. 実行日と実行環境。
3. 受入条件ごとの合否。
4. 実行commandと結果要約。
5. Seed、fixture、設定値。
6. 性能値と測定条件。
7. 自動試験で確認したこと。
8. 手動で確認したこと。
9. 未確認事項、既知の制約、次への持ち越し。

ファイル番号は予定です。既存docsと衝突する場合は連番を調整し、[ドキュメント索引](README.md)を更新します。

## 9. 変更管理

- 計画変更は、変更理由、影響するMilestone、受入条件への影響を記録する。
- 実測で不合格になった条件を削除して完了扱いにしない。
- 不合格条件をMVP対象外へ変更する場合は、ユーザー判断として記録する。
- 実装と文書が矛盾した場合は、実際のコードと試験結果を確認し、文書を最新化する。
- commitとpushは別操作として扱い、明示的な依頼があるまでpushしない。
